# RSVP Lock (Freeze New Registrations) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze new "yes" RSVPs for a single campaign (`8a58fd6d-4b38-4442-bbd2-80c38abb16d8`) while leaving everyone who already said yes fully functional, and leaving every other campaign untouched.

**Architecture:** A new `campaigns.rsvp_locked` boolean (default `FALSE`, flipped to `TRUE` only for the target campaign in the migration's data statement) gates one transition in `POST /api/gift/[token]/rsvp`: a token whose current `attending` is not already `true` cannot set `attending: true` while its campaign is locked. The employee-facing view derives its render branch (RSVP form / "event full" message / QR-gift view) through a single pure function shared between the page and its test, mirroring the existing `summarizeArrival` pattern in `src/lib/arrival.ts`.

**Tech Stack:** Next.js App Router API routes, Supabase (Postgres + service-role client), Vitest (`environment: 'node'`, no component-rendering tests in this repo — UI logic is tested via extracted pure functions, not rendered components).

## Global Constraints

- Default `rsvp_locked` to `FALSE` for every campaign — no behavior change anywhere except the one campaign the migration's `UPDATE` targets.
- Grandfather rule is based on current state, not a snapshot: a token is exempt from the lock only while its `attending` column reads `true` at request time.
- Opting out (`attending: false`) is never blocked, locked or not.
- Headcount edits for already-`true` tokens are unrestricted by this change — only the `false/null → true` transition is gated.
- The admin override endpoint (`PATCH /api/campaigns/[id]/tokens/[tokenId]/attendance`) is untouched — it stays exempt, per its existing "admin override is allowed anytime" comment.
- No admin UI toggle, no numeric capacity logic, no change to `closed_at` / campaign-close behavior.
- Do not apply the migration to the live database as part of this plan — that's a separate deploy step.

```ts
export type RsvpViewParams = {
  supportsArrival: boolean
  attending: boolean | null
  editing: boolean
  allowGiftIfNotAttending: boolean
  rsvpLocked: boolean
}

export type RsvpViewState = {
  showRsvpForm: boolean
  showEventFull: boolean
  showNotComing: boolean
}

/**
 * Decides which panel GiftRedemptionView shows for arrival-certificate
 * campaigns: the RSVP form, the "not coming" message, an "event full"
 * message when rsvpLocked has frozen new yes-answers, or (implicitly, when
 * all three are false) the gift picker / QR view.
 */
export function resolveRsvpViewState(params: RsvpViewParams): RsvpViewState {
  const { supportsArrival, attending, editing, allowGiftIfNotAttending, rsvpLocked } = params

  if (!supportsArrival) {
    return { showRsvpForm: false, showEventFull: false, showNotComing: false }
  }

  // A token is exempt from the lock only while it currently reads attending = true.
  const lockedOut = rsvpLocked && attending !== true
  const wantsFormOrChange = attending === null || editing

  return {
    showRsvpForm: !lockedOut && wantsFormOrChange,
    showEventFull: lockedOut && wantsFormOrChange,
    showNotComing: attending === false && !allowGiftIfNotAttending && !editing && !lockedOut,
  }
}
```
